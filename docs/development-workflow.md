# AI를 활용한 반복 개발 절차

기준: 2026-11-08. 이 문서는 프로젝트의 실행 절차이며 새 자동 실행 서비스는 아니다.

## 과제 한 장

작업마다 목적, 현재 근거, 입력, 수정 파일, 수용 기준, 검증 명령을 정한다. 확인하지 못한 사용자 요구는 가설로 표시한다. 실제 큐브 상태의 정확성과 실제 초보자의 이해도는 별도로 검증한다.

## 반복의 입력과 종료

| 작업 | 다음 반복의 입력 | 종료 기준 |
| --- | --- | --- |
| 기획 | 실제 사용자 관찰, 기존 기능·제약 | 문제·대안·우선순위·검증 과제가 문서화됨 |
| 디자인 | 실제 브라우저 화면·키보드·모바일 검사 | 준비→시연→확인이 읽히고 중요한 결함이 해결됨 |
| 구현 | 실패한 테스트, 실행 오류, 리뷰 근거 | 수용 기준과 해당 검증 명령을 통과함 |

자동 수정 단위는 처음에 최대 3회로 제한한다. 같은 실패가 반복되면 원인·가정·재현 방법을 검토한다. 테스트 삭제나 기준 완화로 완료 처리하지 않는다. 소요 시간·실패 원인·변경량을 실행 기록에 남긴다.

## 스킬과 연결 도구

- 기획에는 아이디어 구체화·명세·계획 스킬을 필요한 단계에서 사용한다.
- 디자인에는 프로젝트 맥락을 읽은 Impeccable 또는 검토한 디자인 스킬 하나를 주도 절차로 정한다.
- 구현에는 기존 코드와 표준 기능을 우선하고, 검증에는 현재 Node 테스트와 Puppeteer 검사를 재사용한다.
- 공개 Claude 스킬을 가져올 때 `SKILL.md`, 상대 경로, 도구 이름, 의존성, Windows 실행 조건과 개별 라이선스를 확인한다. 명령·훅·제품 전용 기능은 별도로 점검한다.
- Figma·Penpot은 시안 협업 필요가 확인될 때 연결한다. 스킬 수나 설치 수를 생산성 지표로 쓰지 않는다.
- 큐브의 상태·회전·목표 도해는 회전 모델의 데이터로 만든다. 이미지 생성은 별도 브랜드·일러스트 과제가 있을 때 사용한다.

## 큐브 사례 검토

1. 시작 조건이 실제 상태와 일치하는지 확인한다.
2. 각 동작과 양언어 설명의 개수가 일치하는지 확인한다.
3. 끝난 상태, 이전 층 보존, 의도된 중간 변화를 확인한다.
4. 반복 사이의 정렬·확인 지점·최종 정렬을 확인한다.
5. 시연 완료와 실물 완료를 구분한다.

## 학습 화면 검토

1. 처음 보는 독자가 시작 수업을 찾을 수 있는지 확인한다.
2. 사례와 잡는 방향을 시연 전에 읽을 수 있는지 확인한다.
3. 한 동작·묶음·확인 지점의 의미가 일관적인지 확인한다.
4. 도움말을 읽는 동안 재생이 멈추고, 화면 되돌리기를 실물 복구로 표현하지 않는지 확인한다.
5. 작은 화면·영어·200% 글자 확대·저장소 차단·JavaScript 미사용을 검사한다.

실물 사용자 평가는 [관찰지](research/usability-study.md)를 사용한다. 설치·외부 계정 권한·공개 배포가 필요해지면 구체적인 작업과 필요한 사용자 행동만 설명한다.
